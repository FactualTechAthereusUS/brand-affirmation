# 06 — Data Model & Admin Store Specification

Source: `src/lib/admin/store.ts` (2655 lines), `seeds.ts`, `selectors.ts`, `cro.ts`, `leads-enrich.ts`, `orders-enrich.ts`, `patients-enrich.ts`, `analytics.ts`, `csv.ts`, `src/integrations/supabase/types.ts`.

## 1. Overall architecture

The entire admin app runs on a **hand-rolled client-side store** (not Redux/Zustand despite the file header comment saying "zustand-style"; it's actually built on `useSyncExternalStore` from React, plus a module-level mutable `state` object). There is no backend for any admin data — everything is generated by a deterministic `seed()` function and persisted to `localStorage`.

- **State container**: module-level `let state: AdminState`, mutated only via `set()` which shallow-merges a patch and notifies subscribers.
- **React binding**: `useAdmin<T>(selector)` — wraps `useSyncExternalStore`, with a small memoization cache that treats same-length arrays with `Object.is`-equal entries as unchanged (avoids re-renders on array literal churn).
- **Persistence**: `localStorage` key **`blissley.admin.v3`**. On load, `load()` merges persisted JSON on top of a freshly-seeded state, running normalization/migration on a few fragile slices (see §5).
- **Hydration**: `hydrateAdmin()` re-runs `load()` and notifies subscribers — used to re-sync state after SSR/client mismatch.
- **All mutations flow through `adminActions`**, a large plain object of methods (not a reducer) that call `set()` directly, described in full in §4.

### 2.1 `SettingsSlice`
Nested configuration object: `business` (legal entity info), `contact` (support emails/phone/URLs), `brand` (logo/primary color), `stripe` (account id, mode, charge model, payout schedule), `pricing` (`PricingConfig` — per-molecule monthly/quarterly/semi-annual prices + upsell prices), `team` (`members`, `require2FA`, `sessionTimeoutHours`, `pendingInvites`), `routing` (pharmacy routing `rules` per product type, `pharmacies` contact list, "Version A" titration-protocol enforcement flags), `states` (`served: Record<StateCode, StateCoverage>`, waitlist config/counts), `notifications` (`alerts: Record<AlertKey, boolean>`, `emailRecipients`, `smsRecipient`, `digest` schedule/items), `compliance` (`baa` records, LegitScript status, HIPAA checklist), `legal` (`docs` — terms/privacy/consent/HIPAA/cancellation text + URLs, and `entity` formation details).

### 2.2 `BuildSlice` (whitelabel funnel/product builder)
- `funnel: FunnelNode[]` — ordered pipeline of pages (`quiz`→`loading`→`sales`→`confirmation`→`portal`), each with editable `FunnelBlock[]` (hero/step/plan-card/cta/faq/quiz-screen) holding freeform `props`.
- `funnelVersion: number` — bumped by `publishFunnel()`.
- `intakeScreens: IntakeScreen[]` — the actual quiz question bank (order, type, question text, answer options, `storeAs` field key, `klaviyoEvent` name, required/locked/active flags). This is the canonical intake definition also consumed by `cro.ts` for screen-level drop-off analysis.
- `products: BuildProduct[]`, `plans: BuildPlan[]`, `upsells: BuildUpsell[]`, `discounts: BuildDiscount[]` — commerce catalog entities, each with a `status: "live"|"draft"|"archived"` lifecycle.
- `emailFlows: EmailFlow[]` — flow metadata (name, email count, status, Klaviyo sync state) — see `05-emails.md` §4 for the mismatch with the actual preview components.
- `pages: BuildPage[]` — marketing page publish status/URLs.

## 5. Persistence, normalization, migration

- Key: `localStorage["blissley.admin.v3"]`.
- `load()`: always builds a fresh `seed()` first, then if a persisted blob exists, shallow-spreads `{...fresh, ...parsed}` and re-normalizes the fragile slices so stale/older persisted shapes don't crash the app:
  - `leads`: `normalizeLeads()` maps each persisted lead through `normalizeLead()`, which defends every enum field (`status`, `intent`, `funnelStep`) against invalid values (falls back to the corresponding fresh-seed lead), clamps `score`/`progressPct` to 0–100, and rebuilds the nested `attribution`/`consent` objects field-by-field with type coercion helpers (`asString`, `asNumber`, `asBoolean`).
  - `integrations`: `normalizeIntegrations()` merges persisted connection state (`status`, `config`, `webhookEvents`, `syncHistory`, `connectedAt`) onto the fresh catalog by `id`, so newly-added integrations in code always appear even if a user's `localStorage` predates them, and removed integrations are dropped.
  - `settings`: `mergeSettings()` does a shallow per-section merge (fresh keys ∪ persisted keys) rather than a deep merge, so brand-new settings sub-fields always exist even against old persisted blobs.
  - `auditLog`: kept only if the persisted value is an array, else reset to seed.
  - `ui`, `tenant`, `tenants`, `build`: shallow-defaulted (`parsed.x ?? fresh.x`), with `tenants` additionally requiring a non-empty array.
- `persist()`: writes the entire `state` object back to `localStorage` as JSON on every `set()` call (no debouncing).
- No versioned migration system beyond the `v3` key suffix and the ad-hoc normalizers above — a `v4` bump would presumably wipe local storage on the next `load()` call for anyone on `v3` shape errors, since there's no explicit migration path between key versions (old key would just be orphaned).

## 6. Multi-tenant `BrandTenant` model

```
BrandTenant = { id, name, logoText, primary, accent, supportEmail, website, stage: "zero"|"ramping"|"live", onboardingStep: 0–6 }
```

Seeded tenants (`SEEDED_TENANTS`):
| id | name | stage | onboardingStep | Data volume on `switchTenant` |
|---|---|---|---|---|
| `blissley` | Blissley | `live` | 6 | Full fresh dataset (all patients/orders/payments/leads/cases/checkIns/conversations/activity/tasks/alerts/notifications). |
| `nova` | Nova Health | `ramping` | 6 | **Sliced** to a partial volume: 60 patients, 45 orders, 60 payments, 12 leads, 8 cases, 6 check-ins, 8 conversations, 8 activity events, 6 tasks, 2 alerts, 4 notifications — simulates a business mid-ramp. |
| `zeroco` | ZeroCo | `zero` | 0 | **Fully empty**: every operational array reset to `[]` and `scenario` forced to `"empty"` — simulates a brand-new, not-yet-launched tenant. |

`switchTenant(id)` re-seeds fresh data then applies the stage-appropriate slice/reset; `updateTenant(patch)` edits the active tenant in place (and mirrors the edit into the `tenants` list); `completeOnboardingStep(step)` monotonically advances `onboardingStep` and flips `stage` to `"live"` once step ≥ 6.

Separately, `setScenario()` provides 4 additional **data-shape overlays** independent of tenant (`healthy` default / `crisis` = payment failures + degraded pharmacies + urgent cases / `churn` = mass cancellations / `launch` = extra pending patients / `empty` = wipe). Scenario and tenant-stage are orthogonal: switching tenant resets scenario, but a user can then independently re-apply a scenario on top of any tenant.

## 7. Supabase — `admin_leads` table

Defined in `src/integrations/supabase/types.ts`. This is the **only** table in the generated `Database` type — i.e. Supabase is provisioned with exactly one table mirroring the client-side `Lead` shape (snake_case columns: `age_hrs`, `assignee`, `attribution` (jsonb), `bmi`, `cart_items` (jsonb), `city`, `consent` (jsonb), `contacted`, `coupon`, `created_at_ms`, `current_weight`, `dob`, `email`, `funnel_step`, `goal_weight`, `id`, `intake_snapshot` (jsonb), `intent`, `last_step`, `last_touch_at_ms`, `loss_reason`, `name`, `outreach` (jsonb), `phone`, `program`, `progress_pct`, `projected_first_order`, `projected_ltv`, `score`, `sex`, `source`, `state`, `state_eligible`, `status`, `tags` (jsonb), `updated_at`, `won_patient_id`), with full `Row`/`Insert`/`Update` variants and no `Relationships`.

**Status: unused / stub.** A repo-wide search finds no code that actually calls `.from("admin_leads")` or otherwise reads/writes this table — the entire Leads feature (`leads-enrich.ts`, `admin.leads.tsx`, etc.) operates purely against the client-side `AdminState.leads` array described above. The Supabase table exists as generated schema (likely from a Supabase migration) that has not yet been wired into the app; it should be treated as a **future integration point**, not a live data path.

## 9. Derived selectors & metric formulas

### `selectors.ts` (general/legacy selectors)
- `todayRevenue`: last `funnelDays` entry's `revenue`.
- `revenueTrend`/`datesTrend`/`newPatientsTrend`/`ordersTrend`: raw or 3-point-smoothed slices of `funnelDays`.
- `failedPaymentsToday`: count of `payments` with `status === "failed"`.
- `refillsDue`: check-ins with `decision === "clear"` and `day` in [85,92].
- `pipelineByPharmacy`: per-pharmacy order counts by stage (with `Math.max` floors to keep demo charts non-zero).
- `queueCounts`: physician/flagged/awaitingReply/refills case counts + unassigned conversation count + overdue check-ins.
- `mrrWaterfall`: hard-coded base ($84,200) + `newMrr`/`churnedMrr` summed over last 30 `funnelDays`, plus fixed expansion/reactivation/contraction constants — **not a real GL waterfall**, illustrative only.
- `abandonedCheckouts`: repurposes the first 10 `leads` as fake "abandoned checkout" rows.
- `acquisitionSpendMix`: groups `campaigns` spend by channel, with fixed brand colors.
- `conversionFunnel`: sessions/intake/paid sums over last 30 days + percentages.
- `sessionsTrend`/`aovTrend`: smoothed derivations from `funnelDays`.
- `activeTrend`: a synthetic smooth upward curve (`180 + i×4.2 + sine/cosine wobble`) — **not derived from real patient counts**.
- `physicianSLATrend`, `approvalRateTrend`, `refillAdherenceTrend`: synthesized trend curves seeded by day index + sine wobble, only loosely anchored to case/funnel data.
- `sessionsByState`: buckets patients by state, scales against a fixed 12,480 total with canned deltas.
- `deviceMix`: fixed constants (Mobile 68% / Desktop 26% / Tablet 6%).
- `trafficSources`: campaign leads grouped by channel + fixed Organic addend (380) + canned deltas.
- `programMovers`: per-program patient/MRR/churn rollups with synthetic sparkline data.
- `paymentsHealth`: synthetic failed/recovered series derived from `paid` volume × fixed rates + sine wobble.
- `insightHeadline`: scenario-aware canned headline/detail/tone strings (used for the dashboard "insight" callout when not using the windowed `pickInsight` in `analytics.ts`).

### `analytics.ts` (window-aware, "real" comparison analytics)
- `makeWindow(state, days, compare)`: builds a `WindowSpec` with `currentSlice`/`priorSlice` genuinely pulled from different `funnelDays` ranges (true prior-period or best-effort YoY), padding short prior slices by repeating the first element.
- `pctDelta`/`ptDelta`/`toneFor`/`formatDelta`: shared numeric helpers (percent change, point change, up/down/neutral tone classification with configurable "positive is good" direction, human-readable delta strings).
- `trendFrom`(+smoothing): generic helper producing `{current, prior, dates, sum, priorSum, deltaPct, last, priorLast}` for any `FunnelDay` field — backs `revenueWTrend`, `sessionsWTrend`, `paidWTrend`, `shippedWTrend`, `intakeWTrend`, `approvedWTrend`.
- `aovWTrend`: per-day `revenue/paid` averaged over window (both current and prior).
- `activeWTrend`: back-derives an "active patients" time series by walking backward from the **live** active-patient count and subtracting each day's `paid` volume — an approximation, not a true historical snapshot.
- `physicianSLAWTrend`: synthesizes per-day median review time from `cases[].slaHrs` average × 6, with sine wobble and a flagged-case penalty; `p90` = max(median)×1.35.
- `approvalRateWTrend`: blends real `cases` approved/denied ratio (50% weight) with `funnelDay.approved/intakeCompleted` ratio (50% weight) plus sine wobble.
- `refillAdherenceWTrend`: baseline = real `checkIns` clear-rate, projected forward with sine wobble + slight upward drift.
- `paymentsHealthW`: real `payments` fail-rate/refund-rate applied against `funnelDay.paid` volume per day, with sine wobble; computes recovery rate as `recovered/failed`.
- `sessionsByStateW`: real patient-state distribution used as a weighting to allocate real `funnelDays` session totals per state (both current and prior), with genuine `pctDelta`.
- `programMoversW`: real per-program patient/MRR/churn from `patients`, real refill % from `checkIns` filtered to that program's patient ids, revenue allocated by patient-count share of window revenue.
- `pickInsight`: scenario-override headlines for `crisis`/`churn`/`empty`; otherwise picks the single largest-magnitude mover among revenue/sessions/approvalRate/refillAdherence/failedPayments (weighted magnitudes) and returns a formatted insight with a deep-link.

### `cro.ts` (funnel/CRO step model)
- `croDay(FunnelDay)`: expands each real `FunnelDay` into a fuller step model (`presellViews/Clicks`, `salesViews/Clicks/Bounces`, `intakeViews/Starts/Completions`, `checkoutStarts`, `purchases`) using **deterministic pseudo-random jitter** (`jitter(ts, salt)`, a sine-hash function — no `Math.random()`, so SSR/client renders match exactly). Presell share ~34–40% of sessions, presell→sales CTR ~52–62%, bounce rate ~41–49%, checkout-starts ≥ purchases with a 1.34–1.56× multiplier.
- `rateMetric()`/`croMetrics()`: computes 10 named conversion/abandonment rates (presell CTR, sales click rate, sales bounce rate, intake start/completion/abandon rate, checkout start/completion/abandon rate, overall conversion rate) each with current value, prior value, point-delta, and full per-day series for charting.
- `steps`: the classic funnel step table (Sessions→Sales views→Sales clicks→Intake started→Intake submitted→Checkout started→Purchased) with cumulative % and per-step drop %.
- `intakeScreenDropoff()`: allocates total intake abandonment across the **actual configured `build.intakeScreens`** (only `active` ones, sorted by `order`) using a friction model keyed by screen `type` (text=3.1, number=2.2, multi=1.9, single=1.2) + a locked-screen penalty (+1.5) + a fatigue term (+0.12×position) + jitter; flags the single worst-performing screen. This is the one place screen-level UX friction is quantified.

### `leads-enrich.ts` (lead KPIs/segmentation)
- `selectLeadKpis`: total/open/hot counts, `abandonedCheckouts30d` (funnelStep ∈ checkout/payment_fail/abandoned_cart within 30d), `recoveryRate30d` (won-within-30d ÷ abandoned-30d), `avgTimeToContactHrs` (mean of last-outreach-ts − createdAt over contacted leads in window), `recoverableRevenue` (sum of `projectedFirstOrder` over still-open leads).
- `SEGMENTS`/`selectSegmentCounts`/`matchSegment`: 9 predefined saved segments (hot·24h, abandoned checkout·30d, intake stalled, payment failed, state-eligible only, Meta/Google paid, DNC, won this month) each a pure boolean predicate over a `Lead`.
- `selectLeads`: search + segment + status-tab filter, generic key/dir sort, pagination.
- `scoreBreakdown(lead)`: re-derives the 4 scoring components (funnel depth ≤55, recency ≤25, channel quality ≤15, engagement ≤20 from reply/connect outreach count + intake depth) for display as a score breakdown bar.

### `patients-enrich.ts` (patient KPIs/segmentation)
- `selectPatientKpis`: total/active/churned/failed counts, `failedRisk` (sum of at-risk MRR), `newThisMonth`/`priorMonth` cohort counts, `churnRate`.
- `SEGMENTS`: 6 predefined segments (month-2 risk, check-in due this week, check-in overdue, high-LTV 6-month plan, win-back candidates, no-portal-login-14d), each a predicate over `(Patient, EnrichedPatient)`.
- `selectPatients`: status/search/segment filter + sort + pagination (segment test requires enriching every candidate patient).
- `selectPatientTimeline`: merges synthetic approval/pharmacy events with real `orders`/`payments` history and login/email-open timestamps into one sorted activity feed.
